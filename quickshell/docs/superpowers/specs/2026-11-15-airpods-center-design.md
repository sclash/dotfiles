# AirPods Center — Native AirPods Control Design

**Date:** 2026-11-15
**Status:** Approved 2026-11-15. Live daemon test passed; see §12.1.
**Scope:** A packaged librepods daemon, a Quickshell AirPods service, a dedicated AirPods launcher, a bar battery badge, keybind and Control Center wiring, specs, tests and Nix wiring.
**See also:** [omarchy-pods](https://github.com/thisisgm/omarchy-pods) (the Omarchy plugin and the forked daemon this borrows), [librepods](https://github.com/librepods-org/librepods) (upstream).

## 1. Intent

The AirPods 5 are connected, but the shell cannot say anything useful about them. BlueZ does not expose `org.bluez.Battery1` for AirPods, so `BluetoothService` has no percentage at all — not left, right, case, charging or in-ear. The only source is Apple's AAP protocol over L2CAP.

`omarchy-pods` already solved the hard part: its `daemon/` is a modified librepods daemon that holds the AAP link, publishes a one-line `status.json` on every change, and accepts `librepods-ctl` verbs. Its `Panel.qml` is Omarchy-specific (`qs.Commons`, `qs.Ui`, `Panel`, `bar`) and cannot run in this shell.

The goal is the same product in our own idiom: per-pod and case battery, listening modes, Adaptive level, Conversation Awareness, One-Bud ANC, ear detection and lid state — in a keyboard-driven launcher and a small bar badge — without polling and without a permanently running extra process.

## 2. Goals

- Show left/right/case (or headset) battery, charging, in-ear and lid state for connected AirPods.
- Change Off / Transparency / Adaptive / Noise Cancellation, the Adaptive noise level, Conversation Awareness, One-Bud ANC and ear detection.
- Run the daemon only while AirPods are connected or the AirPods panel is open; idle memory stays where it is today.
- A bar badge with the lowest battery, a dedicated `SUPER+ALT+A` launcher, and a Control Center entry.
- Render a useful degraded state for every failure: daemon down, AirPods disconnected, unknown model, unreadable/too-new status, `librepods-ctl` error.
- Support AirPods 5 explicitly. The daemon's model map predates it.
- One pure-JS parser with unit tests, plus a QML smoke test.

## 3. Non-goals

- Connect, disconnect, forget, pair or trust. The Bluetooth Center owns those.
- Volume, output device, mute or codec selection. The Audio Center owns those.
- Spatial Audio (no Linux renderer), microphone mode, hearing aids, head gestures, Heart Rate, Find My, cross-device handoff or a phone MAC. The daemon's cross-device feature stays off.
- Changing the daemon's codec policy. It prefers SBC-XQ (453 kbps) over AAC (256 kbps) and may switch the current AAC profile. That is documented, not patched, in this work.
- Non-Apple earbuds. `BluetoothService` keeps working for everything else; this panel only appears for AirPods.

## 4. Constraints

- `AGENTS.md`: nothing machine-specific; the daemon and package are personal layer. Never add a hostname, user path, MAC or model-specific Nix branch.
- `quickshell/AGENTS.md` and `STYLE.md`: `Theme.*`/`Icons.*` only; no hard-coded hex or glyphs; one `Process` per subsystem inside `services/`; launchers never poll; card 560–640 px; `Esc` closes; vim `j/k` and `/` filter; every component has a degraded state.
- The daemon is GPL-3.0 and stays a separate work. The UI takes the MIT `Model.js` and the portable parts of `Service.qml`; the Omarchy `Panel.qml` is not copied. Attribution stays in the file headers.
- AirPods pairing keys (`magicAccIRK`, `magicAccEncKey`) are generated by the daemon and live only in `~/.config/AirPodsTrayApp/AirPodsTrayApp.conf`, mode 0600. They are not user-provided credentials, so they do not go in the SOPS template, and they are never logged, printed or committed.
- The live AirPods are the test device. A live test is allowed, but it must not leave the daemon running, change the paired-device config, or play audio unexpectedly.
- A flake only sees tracked files: `git add` the new patch and QML files before `nix build`/`nix eval`.

## 5. Approaches considered

### 5.1 What to reuse

- **A. Reuse the daemon, write our own UI (chosen).** The daemon owns AAP, pairing, encryption, BLE advertisements and ear detection. Its JSON interface is small and stable. The UI is ours: a 300–400 line launcher in the Audio Center pattern and a 100-line service.
- **B. Port the Omarchy plugin.** Its `Panel.qml` imports `qs.Commons`/`qs.Ui` and Omarchy's `Panel` base; porting the base is more code than writing the panel. The MIT `Model.js` and most of `Service.qml` are already portable, so only the view needs replacing.
- **C. Use `pkgs.librepods` 0.2.5.** The old Qt tray app has no `status.json`, no `status` verb, no Pro 3 or AirPods 5 model map and no `--headless`. It cannot feed a Quickshell service.
- **D. Build our own.** A full AAP stack means reimplementing L2CAP, Magic Pairing, AES and the BLE RPA advertisements — months of reverse engineering and fragile firmware chasing. A battery-only BLE reader is smaller, but it cannot control modes or ear detection, and scanning concurrently with the audio link is what the omarchy README's issue 26 tracks as crackle.

A wins. B is useful only for its parser and service, which A already reuses.

### 5.2 When the daemon runs

- **Always on:** simplest, but the daemon's own notes measure 46 MB RSS for `--headless`; the shell is already around 192 MB idle and `SPECS.md` targets < 200 MB.
- **Only while the panel is open:** idle stays clean, but the bar badge, ear detection and low-battery notifications disappear.
- **While AirPods are connected or the panel is open (chosen):** the full product while the device is in use, zero extra idle cost when it is not. Detection uses the existing `BluetoothService` poll, plus the panel-open fallback before that poll catches up.

## 7. Daemon package and unit

The package is a `stdenv.mkDerivation` in `nixos/programs/librepods.nix`, imported by `nixos/programs/quickshell.nix` with `pkgs.callPackage`:

- `src = fetchFromGitHub { owner = "thisisgm"; repo = "omarchy-pods"; rev = "f35dbc451b386d5ecebf50436ee4a49def059735"; hash = "…"; }`
- `sourceRoot = "source/daemon"`.
- `nativeBuildInputs = [ cmake pkg-config qt6.wrapQtAppsHook ]`.
- `buildInputs = [ libpulseaudio openssl qt6.qtbase qt6.qtconnectivity qt6.qtdeclarative qt6.qtquick3d qt6.qttools ]`.
- `cmakeFlags = [ "-DBUILD_TESTING=OFF" ]`.
- `patches = [ ../patches/librepods-airpods5.patch ]` (or `postPatch` if the patch needs a filename).
- `meta.license = lib.licenses.gpl3`, `mainProgram = "librepods"`.

The unit is a user service, **not** enabled and not `WantedBy`. `AirPodsService` starts and stops it on demand:

- `ExecStart = "${librepods}/bin/librepods --headless"`.
- `Restart = "on-failure"`, `RestartSec = 5`.
- `PartOf = "graphical-session.target"` so a session exit stops it.
- `UMask = "0077"`, `StateDirectory = "librepods"`, `StateDirectoryMode = "0700"`, `ConfigurationDirectory = "AirPodsTrayApp"`, `ConfigurationDirectoryMode = "0700"`.
- `ProtectSystem = "strict"`, `ProtectHome = "read-only"`, `ReadWritePaths = [ "%t" ]`; the state and config directories are the writable carve-outs.
- `PrivateTmp`, `NoNewPrivileges`, `CapabilityBoundingSet = ""`, `RestrictSUIDSGID`, `RestrictNamespaces`, `LockPersonality`, `SystemCallArchitectures = "native"`, `ProtectKernel*`, `ProtectClock`, `ProtectHostname`.
- `RestrictAddressFamilies = [ "AF_UNIX" "AF_BLUETOOTH" "AF_NETLINK" ]`.
- `Environment = [ "PATH=${librepods}/bin:${pkgs.bluez}/bin:${pkgs.coreutils}/bin" ]` so the daemon's `bluetoothctl` connect/disconnect verbs work. Our panel does not use them, but the daemon's own handlers do.
- `librepods` is added to `home.packages` so `librepods-ctl` is on the user's `PATH`; the QML calls it by name, like `wpctl` and `bluetoothctl`.

The daemon's default state and config paths match the unit: `QStandardPaths::GenericStateLocation` → `$XDG_STATE_HOME/librepods/status.json` (normally `~/.local/state/librepods/status.json`) and `QSettings("AirPodsTrayApp", "AirPodsTrayApp")` → `~/.config/AirPodsTrayApp/AirPodsTrayApp.conf`.

## 8. Daemon lifecycle

`AirPodsService` owns a small state machine:

- `wantDaemon` is true when either a connected `BluetoothService` device has `isAirPods`, or `AirPodsCenter.isOpen` is true, or the current status file says `connected: true` (adopt a daemon that survived a shell restart).
- `daemonActive` is true when `status.json` exists, even if the line cannot be parsed: an unreadable line still proves the daemon is running and writing. It is false when the daemon removes the file on exit.
- On every `BluetoothService.dataUpdated`, on panel open/close and on shell start, `reconcile()` compares the two:
  - `wantDaemon && !daemonActive` → `systemctl --user start librepods.service`.
  - `!wantDaemon && daemonActive` → `systemctl --user stop librepods.service`.
- Only one lifecycle `Process` runs at a time; a second reconcile is queued, not dropped.
- A start failure sets `lastError` and does not retry on every 5-second Bluetooth poll. The next connect or panel open retries.
- When the panel opens before `BluetoothService` has caught up (or the AirPods were renamed), the open itself starts the daemon; the panel shows "Not connected" until the daemon identifies the device.
- Starting the daemon shows "Connecting…" for up to 8 s. If the status file never appears, the panel shows the `systemctl` error and the journal hint `journalctl --user -u librepods`.
- A shell restart adopts a running daemon; it does not start a second one. The daemon's socket and single-instance behavior are its own, but the status file is the source of truth for the UI.

### 8.1 `BluetoothService`'s `isAirPods`

The daemon itself identifies AirPods by the BlueZ UUID `74ec2172-0bad-4d01-8f77-997b2be0722a` (the Apple AAP service), not by name. `BluetoothService` gets the same flag without a new process or timer: the existing `pollProc` shell command gains an `---SECTION:INFO---` block that runs `bluetoothctl info` for each connected address, and the existing parser adds `uuids: []` and `isAirPods: bool` to each device. The Bluetooth Center ignores the field; `AirPodsService` and the badge read it.

## 9. Parser `airPodsParse.js`

Adapted from the Omarchy plugin's MIT `Model.js`, with attribution. Pure, `.pragma library`, no QML imports, so it runs in `qmltestrunner` and in any JS harness.

- Constants: `NOISE_OFF/ANC/TRANSPARENCY/ADAPTIVE`, `LID_OPEN/CLOSED/UNKNOWN`, `EAR_*`, `LEVEL_UNKNOWN`, `SUPPORTED_SCHEMA = 1`.
- `parseStatus(raw)` returns the full shape on every path: `ok`, `lastError`, `schemaVersion`, `schemaTooNew`, `connected`, `deviceName`, `modelName`, `modelNumber`, `isProSeries`, `isHeadset`, capability flags, `noiseMode`, `adaptiveNoiseLevel`, `oneBudANC`, `conversationalAwareness`, `earDetectionBehavior`, `lidState`, `left`, `right`, `caseBattery`, `headsetBattery`, telemetry counters ignored.
- Empty file, non-JSON, missing `schema_version` and a newer `schema_version` all return a readable `lastError`.
- `availableModes(supportsNoiseControl, supportsNoiseOff, supportsAdaptive)` returns the ordered list; AirPods 1/2/3 and plain AirPods 4 get no listening section.
- `noiseModeName`, `noiseModeVerb`, `earDetectionVerb`, `earDetectionName`, `levelText`, `levelFraction`, `lidText`, `podMeta`, `elideError`.
- The parser does not trust the daemon's capability flags blindly: an older daemon that omits them falls back to the previous behavior (`supportsNoiseControl` true, others from `isProSeries`), exactly as the Omarchy panel does.

## 10. Service `AirPodsService.qml`

A singleton in `services/qmldir`, one `Process` for `librepods-ctl`, one for `systemctl`, one `FileView` for the status file.

- `statePath` from `Quickshell.env("XDG_STATE_HOME")` or `$HOME/.local/state`, plus `/librepods/status.json`. No hard-coded home path.
- `FileView { watchChanges: true; onFileChanged: reload(); onLoaded: applyLine(text()); onLoadFailed: stateGone() }`.
- `refresh()` reloads the file; the settle timer re-reads after an optimistic action because a no-op verb leaves the file untouched.
- `setNoiseMode`, `setAdaptiveNoiseLevel`, `setConversationalAwareness`, `setOneBudANC`, `setEarDetectionBehavior`, `cycleNoiseMode`, `cycleEarDetection`, `refresh`.
- One verb at a time; a verb arriving while one is in flight replaces the queued one (arrow-key repeat). Optimistic value held for 4 s or until the daemon agrees.
- `actionStatus` names the last successful action for 2.2 s.
- `lastError` comes from parse failures or `librepods-ctl` stderr, collapsed to one line.

The verbs, exactly as `librepods-ctl` accepts them:

| UI action | Verb |
|---|---|
| Off / Noise Cancellation / Transparency / Adaptive | `noise:off` / `noise:anc` / `noise:transparency` / `noise:adaptive` |
| Adaptive level | `adaptive:0` … `adaptive:100` |
| Conversation Awareness on/off | `ca:on` / `ca:off` |
| One-Bud ANC on/off | `onebud:on` / `onebud:off` |
| Ear detection one/both/never | `ear:one` / `ear:both` / `ear:off` |
| Refresh / live diagnostic | `status` (the status file is the normal path; `status` is used by the live test) |

## 11. UI

### 11.1 `AirPodsCenter.qml`

A `WlrLayershell` overlay in the Audio Center pattern: width 620, height `min(640, content)`, `Theme.bgLauncher`, `Theme.roundingLauncher`, full-screen dim, `Esc` closes.

Sections top to bottom:

1. **Header** — `AirPods` (uppercase, `Theme.fgMuted`), separator, device name and model. When disconnected: `Not connected` at `Theme.fgMuted`.
2. **Battery** — left pod, right pod, case (or one headset row for Max). Each row: mark, label, level (`--` when unknown), `Charging` / `In ear` hint, and a slim meter. The case row shows `Open` / `Closed` lid when known.
3. **Listening** — only the modes the device has, in the daemon's order: Off (when available), Transparency, Adaptive (when available), Noise Cancellation. Active row uses `Icons.check` at `Theme.success`. Adaptive level appears only while Adaptive is active; `h/l` or `←/→` adjusts by 5 %.
4. **Features** — Conversation Awareness toggle (H2 models), One-Bud ANC toggle (models with a second bud), Ear detection cycle (one out / both out / never), with the current value spelled out.
5. **Footer** — `j/k` move, `Enter`/`Space` activate, `o/t/a/n` modes, `c` CA, `b` One-Bud ANC, `e` ear detection, `r` refresh, `/` filter, `Esc` close. Hints at `Theme.fgDim`.

Keys: `j/k` and arrows move across actionable rows; `Enter`/`Space` activate; `h/l` adjusts the Adaptive slider; `o/t/a/n` select modes directly; `c`, `b`, `e` toggle/cycle their feature; `r` refreshes; `/` filters row labels (a single-device panel still honors the launcher convention); `Esc` first clears the filter, then closes.

Degraded states, each one line plus a hint:

- Daemon not running: `librepods is not running` + `systemctl --user start librepods` hint; the service tries once when the panel opens.
- AirPods disconnected: `AirPods not connected`; battery rows show `--`.
- Unknown model: device name still shows; model line says `Model not recognised`; modes fall back to the daemon's capability flags.
- Status schema too new: `librepods speaks status schema N, this panel reads 1`.
- Empty/malformed status: `Could not read the librepods status file`.
- `librepods-ctl` error: inline at `Theme.critical`, cleared on the next success.

### 11.2 Bar badge `components/bar/AirPodsIcon.qml`

- A `Theme.barIconSlot` square, placed after the Audio icon and before Wi-Fi.
- Text: `Icons.airpods` plus the lowest known level (`L 74%`, `R 74%`, `C 82%` collapsed to the minimum, e.g. `74%`), or just the glyph when a level is unknown.
- Hidden entirely when the daemon is down, no AirPods are connected, or no battery is known (`hasAirPods`/`hasBattery`), so it never sits there with nothing to say.
- Color: `Theme.warning` at ≤20 %, `Theme.accent` while charging, else `Theme.fg`.
- Hover tooltip: device name, model, L/R/case levels, mode, CA/One-Bud/Ear state; `BarToolTip` with `anchorItem`.
- Click toggles `AirPodsCenter`; the badge is read-only over `AirPodsService`.

### 11.3 Theme

`theme/Icons.qml` gains `airpods` (and, if the installed Nerd Font has it, `airpodsCharging`). The codepoint is verified against the font by rendering the glyph, not guessed; the file uses `String.fromCodePoint` for anything above the BMP, as the USB icons do.

### 11.4 Wiring

- `shell.qml`: add `AirPodsCenter { id: airPodsCenter }`; add `airpods` to `closeAllExcept`, `toggle`, `closeAll`, `open`/`close`.
- `Bar.qml`: insert the badge after the Audio icon.
- `ControlCenter.qml`: add `{ label: "AirPods", key: "SUPER+ALT+A", icon: Icons.airpods, target: "airpods" }` to the launcher list.
- `hypr/hyprland.lua`: `hl.bind(mainMod .. " + ALT + A", hl.dsp.exec_cmd("quickshell ipc call launcher toggle airpods"))`.

## 12. AirPods 5 daemon patch

The pinned daemon (2026-09-14) knows up to AirPods Pro 3 and AirPods Max 2, not AirPods 5 (September 2026). The patch, applied in the derivation, is deliberately small and generic:

- Append `AirPods5` to `AirPodsModel` (never insert; `model_int` is persisted).
- `parseModelNumber`: the base `A3531`, `A3532`, `A3533` and the wireless-case `A3439`, `A3440`, `A3441` → `AirPods5`. Apple lists them as two variants, but they differ only in the case and the on-stem volume control, not in the listening features we expose.
- `modelDisplayName`: `"AirPods 5"`.
- `getModelIcon`: the buds silhouette (`pod3.png` / `pod4_case.png`); the daemon's own GUI is unused, so this only keeps its tray coherent.
- `ble/blemanager.cpp` model map: `0x3020` → `AirPods5` (product ID `0x2030`, byte-swapped like the other entries).
- Capabilities: `supportsNoiseOff` true, `supportsNoiseControl` true, `hasH2ListeningFeatures` true (ANC + Adaptive + Conversation Awareness), `supportsOneBudANC` true, `isProSeries` false, `isModelHeadset` false.

The daemon already publishes `model_number` for exactly this case. If the live device reports one of the six model numbers, the patch is confirmed. If the AAP handshake or battery packet differs on AirPods 5, the patch is not enough: stop, report the status file and journal lines, and fall back to the battery-only scope (the bar badge) only with the user's approval.

### 12.1 Live test (2026-11-15)

The unpatched daemon was built from the pinned commit and run with a temporary `XDG_STATE_HOME`/`XDG_CONFIG_HOME` so the real pairing keys were never touched. It connected to the AirPods 5 over AAP and published:

- `connected: true`, `model_number: "A3439"` (AirPods 5 with Wireless Charging Case), `model_name: ""`.
- Left 93 % and right 97 %, both `in_ear: true`.
- `noise_mode: 2` (Transparency), `conversational_awareness: true`.
- `supports_noise_control: true`, `supports_noise_off: true`; `supports_adaptive`, `supports_conversational_awareness` and `supports_one_bud_anc` false, because the model is unknown.

That confirms the battery/AAP path works today and that the patch is only needed for the model name and the H2 capability keys. While connected the daemon pauses BLE discovery, so the case stayed `available: false` and `lid_state: 2` (unknown); the panel must render the case as `--` and omit the lid. The test was stopped cleanly, the temp keys were deleted, and the real `~/.config/AirPodsTrayApp` and `~/.local/state/librepods` were never created.

The post-test card profile was `headset-head-unit` with an LC3 codec because a capture stream was live; the daemon defers its A2DP ladder during capture, as its README says. The SBC-XQ note in §13 applies when playback is on A2DP.

## 13. Memory and codec

- The daemon runs only while AirPods are connected or the panel is open (§5.2). Idle memory is the current shell (~192 MB) with no daemon.
- While connected, the daemon adds its own resident set (the fork's README measures ~46 MB RSS for `--headless`; shared Qt/GLib pages make the incremental cost smaller but non-zero). The bar badge is available exactly while that cost is paid.
- The daemon re-applies the highest-bitrate playback profile, SBC-XQ at 453 kbps, over AAC at 256 kbps, when A2DP is the active profile. The current AAC profile may therefore change when the daemon connects. While a capture stream is live the headset profile stays and the daemon defers its ladder (§12.1). This is the daemon's deliberate default; we do not patch it. If the user prefers AAC, a follow-up can rank AAC above SBC-XQ in `media/profilechoice.hpp`.

## 14. Security and privacy

- The daemon runs as the user. No root, no capabilities, no network sockets (local Bluetooth + D-Bus only).
- Pairing keys live in `~/.config/AirPodsTrayApp/AirPodsTrayApp.conf`, 0600, created by the daemon. They are not in the repo, not in the SOPS template (not user-provided), and never printed; the daemon logs only key sizes.
- `status.json` is 0600 under `~/.local/state/librepods`; the UI reads it as the user.
- The systemd unit hardening is listed in §7. `ProtectHome=read-only` is paired with the state/config directories and `%t` for the control socket.
- The GPL-3.0 daemon remains a separate program. The UI service/parser are our code with MIT-derived pieces; the file headers keep the attribution. The Omarchy panel and Apple's AirPods outlines are not copied.

## 16. Decisions made in this design

- Panel is a dedicated launcher, not an Audio Center section: it matches the omarchy-pods product and keeps the Audio Center's device list clean.
- Keybind `SUPER+ALT+A` (Audio-adjacent; currently free — the only `SUPER+ALT` binds are `h/j/k/l` window swaps).
- Badge after the Audio icon, before Wi-Fi.
- Daemon is started/stopped by the shell, not enabled at login; the unit is still `PartOf=graphical-session.target`.
- AirPods detection is the BlueZ AAP UUID, with the panel-open fallback before `BluetoothService` catches up.
- SBC-XQ stays the daemon's default; AAC preference is a possible follow-up.
- The daemon's low-battery notifications are left on; they arrive through our `NotifService`.
- The panel has no connect/disconnect/forget and no volume/output rows; those stay in the Bluetooth and Audio Centers.
